# Contributing

## Branch strategy

```
feature/<name>  ──▶  dev  ──▶  main
```

- Never commit directly to `main` or `dev`.
- Work on a `feature/<name>` branch (or `chore/<name>`, `fix/<name>` etc.).
- Open a PR to `dev` when the feature is complete.
- `main` receives merges only at stable phase milestones via PR from `dev`.

## Conventional Commits

All commit messages must follow the [Conventional Commits](https://www.conventionalcommits.org/) format:

```
<type>(<scope>): <description>
```

**Types**

| Type       | When to use                                       |
|------------|---------------------------------------------------|
| `feat`     | New feature or capability                         |
| `fix`      | Bug fix                                           |
| `test`     | Adding or updating tests                          |
| `refactor` | Code change that is neither a fix nor a feature   |
| `perf`     | Performance improvement                           |
| `docs`     | Documentation only                                |
| `chore`    | Tooling, CI, dependency bumps, project scaffolding|

**Scopes**

`ingestion` · `kafka` · `spark` · `airflow` · `dbt` · `infra` · `dashboard` · `docs`

**Examples**

```
feat(ingestion): add Binance WebSocket consumer with retry logic
fix(kafka): handle producer timeout on broker restart
chore(infra): add docker-compose health checks for all services
docs: update architecture diagram after Phase 4
```

## Phase workflow

Each phase ends with an explicit list of git commands (generated by Claude Code)
that must be run before starting the next phase. Do not merge to `dev` until
all phase commits are authored and reviewed.
